# 小说管线两遍式地图架构 + 渠道槽位管理 — 设计文档

- 日期：2026-09-26
- 状态：已与用户确认定稿
- 范围：`peixi` 小说处理管线（N1~N4）重构、LLM 渠道/槽位系统、处理页与阅读器联动

## 1. 背景与问题

以 300 万字、约 1200 章的典型网文为基准，现行管线的实测结构问题：

| 问题 | 根因 | 位置 |
|---|---|---|
| 全程 8~15 小时 | ~3000 次 LLM 调用严格串行（N2 逐章 1200 次 + N3 每块 2 次 ×1500 块） | `novel_pipeline.dart` / `novel_commentary_generator.dart` |
| 处理期间阻塞所有视频项目 | `PipelineQueue` 全局串行 | `pipeline_queue.dart` |
| 批注"失忆" | N3 唯一长程记忆是 ≤300 字滚动 digest | `prompts.dart` rollingDigest |
| 伏笔/呼应类批注天生做不出 | 批注模型只看得到过去 | `novel_annotation` prompt |
| N2 产物被浪费 | 章节摘要从未被 N3 读取；人物名单未进批注上下文 | `novel_commentary_generator.dart` |
| O(n²) token 开销 | 人物名单每章全量重发 | `NovelCharacterExtractor` |
| 必须等全书跑完才能读 | 阅读器入口仅 `status == ready` 放行 | `library_page.dart:519` |
| 旧项目断点粗糙 | 断点凭据是单个 `annotatedPara` 整数 | `novel_importer.dart` NovelMeta |

用户明确诉求：①真·边读边处理——导入后几分钟内开读，批注永远领先阅读；②批注拟人化、解释性，可点破"在酝酿什么"但不透露结局，可引用前文具体事实；③AI 自选批注段落，不逐段硬讲；④调用次数与频率优先压低（中转站限速限频），允许摘要粒度妥协，批注质量不妥协；⑤自选 OpenAI 兼容中转站渠道，按用途绑定模型。

## 2. 目标与非目标

**目标**

1. 300 万字全书 LLM 调用从 ~3000 次降到 ~760 次；首屏冲刺（前 10 章批注就绪）1~2 分钟。
2. 小说导入完成即可进阅读器，批注随到随显；批注进度永远领先默认阅读速度。
3. 批注上下文含"故事至今"快照 + 出场人物人设与事件线，能写预示式、呼应式批注且不剧透。
4. 多渠道模型管理：渠道（BASE_URL+KEY+拉取模型）→ 功能槽位绑定。
5. 全局 LLM 并发信号量 + 429 收敛；章/批粒度断点续跑；老项目无缝迁移。

**非目标（YAGNI）**

- 向量检索/记忆库（人物事件线覆盖大部分前文呼应需求，留作后续增强）。
- "读到哪处理到哪省成本"暂停开关（默认顺序跑完全书）。
- 卷级摘要 UI、章节导读卡片。
- 视频管线架构重构（仅顺迁到槽位系统）。

## 3. 总体架构：三趟流水线

```
导入 N1（不变，秒级）
   │
   ▼
地图趟 Map（cheap 槽位，并行）          每 5 章一次调用 → 240 次
   输出/章：150~300字摘要、人物增量（新人物/人设变化/主要标记）、
            人物关键事件（主角配角各 1~2 条）、本章出场人物名单
   人物名单按 50 章窗口快照进 prompt；窗口末合并去重
   │
   ▼
故事地图趟 Digest（cheap 槽位，顺序）   每 10 章合成一次 → 120 次
   逐章把"当时的滚动摘要"快照写进该章行（digest_before）
   │
   ▼
批注趟 Annotate（analysis 槽位）        每 3 章一次调用 → ~400 次
   上下文 = 该章 digest_before + 出场人物人设/事件线 + 前一两章摘要 + 整章正文
   模型自选段落与数量输出 L1~L4 批注；按章分组校验落库
```

核心不变式：**批注只读"该章之前"的信息（不剧透），但地图趟让系统知道全局**——因此批注能写"男主心里开始犯嘀咕"式预示而不泄露走向。三趟之间只通过数据库衔接，天然支持并行、崩溃续跑、取消。

调用账本（300 万字）：地图 240 + 摘要 120 + 批注 ~400 ≈ **760 次**（现状 3000+ 的约 1/4）。

### 可调参数（settings，带默认值）

| 参数 | 默认 | 说明 |
|---|---|---|
| `novel.mapBatchChapters` | 5 (1~10) | 地图趟每次调用覆盖章数 |
| `novel.digestBatchChapters` | 10 | 摘要合成批大小 |
| `novel.annotateBatchChapters` | 3 (1~10) | 批注趟每次调用覆盖章数 |
| `novel.initialBurstChapters` | 10 | 首屏冲刺章数 |
| `novel.mapLeadChapters` | 20 | 地图需领先批注的章数 |
| `llm.concurrency` | 2 (1~8) | 全局并发信号量 |
| `llm.minRequestIntervalMs` | 0 | 请求最小间隔（频控友好） |

### 批次边界确定性

所有批量切分按章号静态计算（`start = 首个未处理章号向 5 对齐` 等），不依赖运行时状态。保证：崩溃续跑批边界一致、响应缓存（键 = 渠道+模型+消息）在重跑时命中。

## 4. 渠道与槽位系统

### 4.1 数据

- 新表 `llm_channels`：id、name（显示名）、base_url、enabled、created_at；api_key 存 secure storage（沿用 `SettingsRepository` 机密通道，键含 channel id）。
- 槽位绑定存 settings 表：`llm.slot.<slot>` = `{"channelId":n,"model":"..."}`。
- 槽位枚举（对齐现有 tier 语义，视频侧顺迁）：
  - `summary` 轻量整理：地图趟、故事地图合成、知识卡补充
  - `analysis` 深层分析：小说批注、视频场景解说
  - `vision` 视觉理解：视频关键帧（沿用）

### 4.2 行为

- 设置页新增「模型渠道」：增删改渠道，每渠道可"测试连接 / 拉取模型列表"（GET /models，结果缓存本地供下拉选择）。
- 槽位页：每个槽位两段下拉——渠道 → 该渠道模型列表中的模型。
- `LlmService`：`chat/chatJson` 参数 `tier` 改为 `slot`，内部解析到渠道的 BASE_URL/KEY/模型；响应缓存键加入渠道标识（防不同中转站同名模型串缓存）；`purpose` 日志不变。
- **迁移**：现有单配置（base_url + key + cheap/standard/vision）首启自动生成"默认渠道" + 三个槽位绑定，老用户无感。
- 视频管线调用点（人物映射、场景解说、知识卡、视觉）同步改为槽位参数，行为不变。

## 5. 数据模型变更（drift 迁移）

| 变更 | 字段/表 | 用途 |
|---|---|---|
| `chapters` 加列 | `map_done` (bool) | 地图趟按章完成标记 |
| | `annot_done` (bool) | 批注趟按章完成标记 |
| | `cast_ids` (JSON, List<int>) | 本章出场人物 id（地图趟写入，批注趟读） |
| | `digest_before` (text, nullable) | 该章开读时的故事地图快照 |
| 新表 `character_events` | id, project_id, character_id, chapter_idx, event | 人物关键事件时间线（批注前文呼应的召回源） |
| `characters` 加列 | `major` (bool) | 主要人物标记；名单进 prompt 按 major+近期活跃过滤，防膨胀 |
| 新表 `llm_channels` | 见 4.1 | 渠道定义 |
| settings 表 | 槽位绑定 + 新参数 | 见 3/4 |

### 旧项目迁移回填（schema 升级时执行）

1. `chapters.summary` 非空 → `map_done = 1`。
2. `meta.annotatedPara >= chapter.end_para` → 该章 `annot_done = 1`。
3. 旧 `meta.digest` → 写入**第一个未批注章**的 `digest_before`（它正是旧引擎在该断点的"故事至今"）；故事地图趟从该章继续向后合成。
4. 已有 annotations / characters / knowledgeCards 原样保留。
5. 旧 `annotatedPara` 字段保留但不再使用（NovelMeta 标记 deprecated）。

## 6. 调度器与"导入即用"

### 6.1 流程

```
导入完成（秒级）→ 小说项目立即可进阅读器（解除 ready 闸门，见 6.3）
   │
   ▼
① 首屏冲刺：前 initialBurstChapters(10) 章
   map(2次调用) → digest(1次) → annotate(3~4次，首屏用大批次)
   并发 2 下约 1~2 分钟 → 阅读器提示「前 N 章批注已就绪」
   │
   ▼
② 跟随模式（后台持续，全部调用共享全局信号量，优先级队列）
   map:      保持完成章数 ≥ 批注完成章数 + mapLeadChapters(20)
   digest:   保持 digest_before 就绪章数 ≥ 批注完成章数 + 1
   annotate: 按书序推进直至全书完成
```

### 6.2 调度原则

- **处理顺序 = 阅读顺序**（书序），因此批注天然领先阅读速度（人读一章按分钟计，机器批 3 章按十秒计，即使并发 1 也追得上）；阅读位置只用于：首屏冲刺优先级、UI"领先 N 章"展示。不做"停在读到位置省成本"。
- 优先级队列：`annotate(含阅读窗口附近的章) > map(领先保活) > digest(追赶)`；首屏冲刺期间全并发让路。
- 多本小说可同时挂调度器（调用经全局信号量交错）；视频管线继续走原 `PipelineQueue` 串行车道，互不阻塞（LLM 调用与 ffmpeg/ASR 资源不同类）。
- 取消：登记取消标记后不再派发新调用，在批/章边界优雅退出；已完成批已落库。
- 失败：批/章级失败按现有阶段失败语义落盘（status=failed + failedStage），重试从缺失章续跑。

### 6.3 入口与状态

- `library_page`：novel 项目在 `status >= imported`（即非 failed 的任何状态）即显示「开始阅读」；卡片徽章改为显示批注进度百分比（`annot_done` 章数/总章数）。
- `ProjectStatus` 里程碑沿用：imported → mapped（地图趟全书完成）→ commentaryDone（批注趟全书完成）→ ready；处理中状态允许进阅读器是本次新增语义。
- 处理页：novel 阶段时间线改为两条泳道「地图 X/Y 章」「批注 A/B 章」+ 「领先阅读 N 章」徽章 + 本书已耗 token（sum llm_logs by project）+ 对已完成章的「重新批注此章」按钮。

## 7. Prompt 设计（三个新/改模板）

### 7.1 novelMap（地图趟，cheap 槽位）

输入：名单摘录（major+近期，≤~80 行，仅 name+profile）+ 连续 N 章正文（每章带章号与标题）。
输出 JSON：
```json
{"chapters":[{"idx":0,"summary":"150~300字，含本章转折与人物关系变化",
              "cast":["出场人物名"],
              "events":[{"name":"人物名","event":"本章该人物的关键事件，一句"}],
              "characters":[{"name":"新人物","profile":"一句话人设","major":false}]}]}
```
规则：只依据文本，禁止编造；龙套不收录；events 只记对后文可能有意义的事。

### 7.2 digestMerge（故事地图趟，cheap 槽位）

旧滚动摘要 + 最近 10 章摘要 → 新摘要 ≤400 字。必须保留：人物关系与立场、当前悬念、未回收伏笔清单（逐条短语）。输出 `{"digest":"..."}`。失败降级：旧摘要 + 新章摘要拼接截断（沿用现有兜底）。

### 7.3 novelAnnotate v2（批注趟，analysis 槽位）

人设：**陪读老友**，不是贴标签机器。
上下文分节：`[故事至今] digest_before`、`[出场人物] 人设+历史事件线（每人物 ≤3 条）`、`[前文摘要] 前一两章`、`[本章正文] 段落带全局 para_idx`。
三条硬规则写入 prompt：
1. 只基于"故事至今"与本章前文，**绝不透露**后文走向与结局；
2. 可以写"在酝酿什么"（"他心里开始犯嘀咕，总觉得这事没完"），但不点名后果；
3. 引用前文必须用人物事件线里的**具体事实**，不许空泛。

输出 JSON：`{"chapters":[{"idx":n,"annotations":[{"para_idx":p,"type":"L1|L2|L3|L4","content":…同现有结构}]}]}`。
密度指令：每章 3~8 条为基准、可上下浮动，宁缺毋滥；每条 2~4 句解释性叙述；禁止"此处埋下伏笔"式标签短语。
L1~L4 类型与 content 结构**不变**（阅读器、知识卡、SRS 依赖）。

## 8. 错误处理与降级

| 场景 | 处理 |
|---|---|
| 批注批 JSON 解析连续失败 ×2 | 自适应降批：批大小减半重试 → 单章兜底（记录降批事件） |
| 地图批解析失败 | 同上降批逻辑 |
| 摘要合成失败 | 拼接截断兜底，不阻塞批注主线（沿用） |
| 429/5xx/网络错误 | 现有 4 次退避重试；新增：429 时调度器暂停派发并收敛在途（退避结束后恢复） |
| 月度预算用尽 | `LlmBudgetException` 原样落阶段失败（沿用） |
| 崩溃/强退 | 批/章状态已落库，重试续跑；批次边界静态保证缓存命中 |
| 旧项目 | 第 5 节迁移回填，无缝续跑 |

## 9. UI 变更汇总

- **设置页**：新增「模型渠道」区块（渠道 CRUD + 测试/拉模型）与「功能槽位」绑定。
- **处理页**：novel 泳道进度（地图/批注）、领先阅读徽章、token 花费、单章重跑按钮。
- **库页**：novel 卡片「开始阅读」提前到导入后即可用；徽章显示批注百分比。
- **阅读器**：批注缺失段落不显示（现状）；本章批注生成完成后自动刷新（订阅管线事件流）；顶部轻提示"本章批注生成中"。

## 10. 测试策略

- **单元**：批次切分静态对齐、窗口名单合并/去重、摘要降批逻辑、调度优先级与领先保活、槽位解析与缓存键含渠道、迁移回填五条。
- **集成（假 LLM，脚本化响应）**：10 章小书全链路 → 校验 chapters/character_events/annotations 落库与里程碑流转；中途杀进程 → 续跑无损；取消 → 批边界优雅退出。
- **冒烟（真渠道）**：导入一本真实网文（≥100 万字），验证首屏冲刺耗时、频控表现、阅读中批注自动出现。
- 现有测试全量回归（视频侧槽位迁移不改变行为）。

## 11. 落地顺序（每步可独立验证）

1. 渠道与槽位：`llm_channels` 表、设置页、`LlmService` 槽位化 + 并发信号量 + 429 收敛（视频侧顺迁）。

3. 三趟引擎：NovelMapPass（窗口+批量+降批）→ DigestPass → AnnotatePass（批量+降批+按章落库）。
4. 调度器：首屏冲刺、优先级队列、领先保活；`PipelineController` 接入；库页/处理页/阅读器 UI。
5. 集成测试 + 冒烟 + 参数默认值调优。

## 12. 关键决策记录

| 决策 | 结论 | 来源 |
|---|---|---|
| 产品形态 | 真·边读边处理（导入即读，批注跟随） | 用户选择 |
| 剧透尺度 | 可预示"在酝酿什么"、可引用前文具体事实，绝不透露走向结局 | 用户原话定调 |
| 批注单元 | 整章/多章批量，模型自选段落，宁缺毋滥 | 用户提议 |
| 前文细节召回 | 人物事件线（结构化轻量），不做向量检索 | 用户表示可不带前文 |
| 调用预算 | 全书 ~760 次；并发默认 2 + 最小间隔；摘要可粗、批注不降级 | 用户中转站限频约束 |
| 模型接入 | 多渠道 + 按用途槽位绑定，拉取模型列表选择 | 用户要求 |
| 处理范围 | 默认顺序跑完全书，不做省成本暂停 | 助手建议，用户确认 |
